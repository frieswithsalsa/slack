# Code Review Excellence

Скилл для сильного, системного и конструктивного ревью ради улучшения качества кода и поддержки кода в чистоте.

## Когда применять

- Ревью PR / diff / коммитов / файлов / функций.
- Поиск дефектов, архитектурных рисков, регрессий, пробелов в тестах.
- Оценка изменений перед merge или CI-предпроверкой.

## Когда не применять

- Пользователь просит только объяснить код без оценки качества.
- Нет изменённого scope для ревью.

---

## Core Principles

### 1. Mindset ревью

Цели:

- Найти баги, edge-cases и уязвимости.
- Снизить риск регрессий до merge.
- Улучшать дизайн и архитектуру.

Не цели:

- Делать ручную работу, которую должен делать линтер.
- Переписывать чужое решение только «под себя».

### 2. Качественный фидбек

Хороший фидбек:

- Конкретный и применимый.
- Приоритизированный по критичности.
- Объясняет риск и сценарий проявления.
- Содержит реалистичный путь исправления.
- Вместо «переделай так» предлагает вариант и объясняет выигрыш.

Примеры:

```markdown
❌ Плохо: "Это неправильно."

✅ Хорошо: "В этом `useEffect` нет отмены запроса. При быстром
переключении фильтров можно получить race condition и перезаписать состояние
устаревшими данными. Добавь `AbortController` или guard по requestId."

❌ Плохо: "Переименуй это."

✅ Хорошо: "[незначительно] Название `data` слишком общее для этого модуля.
`itemsByCategory` / `responseItems` читается понятнее.
Неблокирующее замечание, если в команде нет другого стандарта."
````

### 3. Объективность

* Явно отделяй факт дефекта от предпочтения.
* Не дублируй одно и то же замечание по каждому месту.
* Не выдумывай проблемы без подтверждения в коде.
* Не блокируй merge по вкусу или перфекционизму.
* При неоднозначности помечай как вопрос: `❓`, а не как дефект.

## Scope и глубина ревью

* Поддерживаемые входы: diff, список файлов, сырой код, ссылка на файл, функция.
* Ревьюить только переданный scope, не выходить за его границы.

Режимы:

* **Полный** — по умолчанию. Используются все метки: `🔴 [блокер]`, `🟡 [важно]`, `🟢 [незначительно]`, `💡 [предложение]`.
* **Быстрый** — если пользователь просит «быстрое ревью», `quick review`, «только критичное». Используются только
  `🔴 [блокер]` и `🟡 [важно]`.

**Что не ревьюить вручную:**

* Форматирование кода: eslint / stylelint / prettier и автолинтеры.
* Порядок импортов.
* Линт-нарушения без архитектурного или поведенческого риска.

---

## Приоритеты проверки

1. Архитектура и принципиальные соглашения: `UI / logic / data`, `app / view`, `server / client`.
2. Корректность бизнес-логики и риски регрессий.
3. Надёжность, обработка ошибок, наблюдаемость.
4. Производительность.
5. Безопасность.
6. Поддерживаемость и устранение дублирования.

Детальные чеклисты по каждому пункту — в [`references/checklists.md`](./references/checklists.md).

### Поддерживаемость

* Ясные и предметные имена сущностей.
* Небольшие функции с одной ответственностью.
* Нет магических чисел / строк без контекста.
* Нет дублирования бизнес-логики и однотипных веток.
* Повторяемые фрагменты вынесены в хук / утилиту / общий компонент.

## Процесс ревью

### Фаза 1. Сбор контекста

1. Прочитать описание PR / задачи и цель изменений.
2. Зафиксировать масштаб изменений и выбрать стратегию.
3. Для больших PR ревьюить по логическим чанкам с явной фиксацией покрытого scope.
4. Понять бизнес-требование и ожидаемое поведение.
5. Отметить релевантные архитектурные ограничения.

### Фаза 2. High-level ревью

1. Архитектура и дизайн:

* решение соответствует задаче;
* нет более простого и надёжного пути;
* подход консистентен с существующим модулем.

2. Организация файлов:

* код расположен в правильных слоях / директориях;
* нет лишнего дублирования и расползания ответственности.

3. Тесты:

* есть ли тесты для рискованных изменений;
* покрыты ли ключевые edge-cases;
* нет ли потери контрактов при рефакторинге / миграции.

### Фаза 3. Детальный проход по файлам

Проверять по чеклистам из [`references/checklists.md`](./references/checklists.md).

### Фаза 4. Итог и решение

1. Сгруппировать замечания по приоритетным меткам.
2. Коротко отметить сильные стороны изменения.
3. При сложной правке предложить парный разбор.

## Приоритеты комментариев

* `🔴 [блокер]` — блокирует merge: security, data loss / corruption, race conditions, сломанный контракт или функционал.
* `🟡 [важно]` — нужно исправить или аргументированно обсудить: регрессии, архитектурные риски, missing error handling,
  существенные perf-проблемы.
* `🟢 [незначительно]` — неблокирующее улучшение: нейминг, локальная читаемость, мелкий рефакторинг.
* `💡 [предложение]` — альтернативный подход или улучшение дизайна решения.

---

## Источник изменений

* Если передан `PR ID`, ревьюить только этот PR.
* Если `PR ID` не передан, ревьюить коммиты текущей ветки относительно основной ветки проекта.
* Для определения состава изменений использовать доступные инструменты работы с VCS / code review system.
* Если `PR ID` не передан, текущая ветка является основной веткой проекта и не указан конкретный scope: файл / функция /
  коммит, ревью не выполнять и вернуть короткое пояснение.

## Что исключать из анализа

* Код вне scope PR / diff / запроса.
* Скриншоты / снапшоты:

  * `**/__screenshots__/**/*.png`
  * `**/__image_snapshots__/**/*.png`
  * `**/__snapshots__/**/*.snap`
* Mock / fixture JSON:

  * `**/mocks/**/*.json`
  * `**/fixtures/**/*.json`
  * `**/test-data/**/*.json`
  * `**/mock*.json`
* Lock-файлы:

  * `**/package-lock.json`
  * `**/yarn.lock`
  * `**/pnpm-lock.yaml`
  * `**/npm-shrinkwrap.json`
* Сгенерированный / vendored код и артефакты сборки.
* Не применять к тестам те же строгие критерии, что к production-коду.

## Эволюционная консистентность

Новый код должен соответствовать локальным паттернам модуля.

Отклонение допустимо как осознанная миграция, если есть сигналы:

* цель смены подхода зафиксирована в задаче / PR;
* изменены соседние участки тем же подходом;
* есть план продолжения.

Если сигналов нет:

* фиксируй как `🟡 [важно]`: `architecture` / `maintainability`.

Если сигналы есть:

* не помечай как дефект;
* добавь `Migration note`: что меняется, зачем, какой scope мигрирован, что осталось.

## Формат ответа

Используй только этот формат. Не добавляй альтернативные шаблоны и секции.

Локальные комментарии:

* Начинай с метки приоритета: `🔴 [блокер]` / `🟡 [важно]` / `🟢 [незначительно]` / `💡 [предложение]`.
* Для `🔴 [блокер]` и `🟡 [важно]` обязательно указывай:

  * **Файл:** `project-root-relative/path/to/file:line`

    * ✅ Пример: `src/view/libs/getSomething.ts:42`
    * ❌ Нельзя: `libs/getSomething.ts:42`, `getSomething.ts:42`
  * **Проблема:** риск и сценарии проявления.
  * **Решение:** конкретный путь исправления. Приложить конкретный сниппет кода, если это возможно.

Порядок секций в ответе:

1. `## Summary`
2. Локальные комментарии с метками приоритета, без отдельного заголовка секции
3. `## Questions`, только если контекст неполный
4. `## Docs Used`

Правила:

* В `## Summary` коротко укажи, что проверено и общий итог по качеству.
* Ниже перечисляй только замечания в формате локальных комментариев выше.
* Если замечаний нет, пиши одной строкой: `блокер/важно issues не найдено`.

---

## Edge cases

* Если контекст неполный: перечислить недостающие данные и пометить выводы как предварительные.
* Если код хороший: явно написать, что критичных замечаний нет.
